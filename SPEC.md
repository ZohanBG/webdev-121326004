## Project option
<!-- One line: lab booking, study groups, club events, or the own project the lecturer approved. -->
Lab booking.

## Goals
- A student signs in, picks a day, sees which workstations are free in each time block, books one block and cancels their own booking before it starts.
- A student can describe what they need in plain words ("quiet place with two monitors, Thursday afternoon") and gets one concrete free slot suggested, which they confirm with one press.
- Lab staff add labs and workstations (with features such as quiet or dual-monitor), take a workstation out of service, cancel bookings on it when needed, and see every booking in every lab for any day.
- The same booking rules apply whether a person uses the web UI or an agent uses the MCP server.

## Non-goals
- No payments or deposits: every booking is free.
- No email, SMS or push notifications: students check "My bookings" on the site.
- No recurring bookings ("every Tuesday"): each booking is one block on one day.
- No group bookings: one booking is one person on one workstation.
- No waitlist: a taken block is simply not offered.
- No self-service staff accounts: the staff role is given by a seed or by an existing staff member, never by sign-up.
- No bookings by staff: staff manage labs, students book.
- No mobile app and no chatbot: one responsive web UI; the model only suggests a slot.
- No password reset by email and no email verification flow for local sign-up.

## Constraints
- Node 22 with Express, PostgreSQL (Neon in production), plain HTML, CSS and JavaScript in the UI. Tests with Vitest and v8 coverage.
- Three layers that never skip each other: `routes/` → `services/` → `data/`. No SQL outside `src/data/`. Every rule (ownership, limits, roles) is checked in `src/services/`, never in a route handler.
- Every schema change is a new numbered migration in `migrations/`; a migration that has run is never edited. Foreign keys use `ON DELETE RESTRICT`: the app never deletes labs or workstations, it takes them out of service, so booking history is never lost.
- Passwords are stored only as a bcrypt hash, never as readable text. Sessions are server-side and the database stores only a hash of the session id, never the cookie value itself; the cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in production.
- No secret is ever in a file in the repo: keys go in Codespaces secrets and the hosting settings; `.env.example` holds names only. Seed account passwords come from `SEED_PASSWORD`.
- Time blocks are fixed: Monday to Friday, 08:00–20:00, six 2-hour blocks, in Europe/Sofia time; times are stored as UTC. Deliberate decision: six fixed blocks keep the day view readable at 380 px and make "one booking per block" a simple unique index, instead of overlap checks on free-form times.
- A slot is one workstation in one block on one date. The REST API sends it as `{ "workstationId": 7, "date": "2026-11-19", "block": 3 }`, with blocks numbered 1–6 (1 = 08:00–10:00 … 6 = 18:00–20:00). The MCP tools and the model use the same slot as one string id, `<workstationId>:<date>:<block>` (e.g. `7:2026-11-19:3`), which the service parses into those three fields before applying the same rules.
- A block is "upcoming" until its start time. Once a block has started it can no longer be booked or cancelled.
- A student cancels only their own bookings. Staff can cancel any upcoming booking (e.g. a broken workstation); every cancelled row records who cancelled it in `cancelled_by`.
- A student holds at most 3 upcoming active bookings and at most one booking per time block. Bookings are possible for upcoming blocks up to 14 days ahead.
- "One workstation, one block, one active booking" and "one student, one block, one active booking" are each enforced by a unique index on active bookings in the database, not only by a check in code. The 3-booking limit is checked inside a transaction that locks the student's row, so two parallel requests cannot both pass it.
- Workstation features come from a fixed list of 16 ids in four groups, kept in one place in code (`src/services/features.js`, with a label for each); the database's CHECK repeats the ids and a test keeps the two equal. Hardware: `high-end-pc` (High-end PC, 32 GB+ RAM), `gpu-cuda` (NVIDIA GPU, CUDA), `gpu-server` (Access to the GPU server), `dual-monitor` (Dual monitors), `drawing-tablet` (Drawing tablet). Software / OS: `linux`, `windows`, `matlab`, `cad` (AutoCAD / SolidWorks), `docker-vm` (Docker / VM ready). Lab equipment: `electronics-bench` (oscilloscope, soldering), `network-rack` (Cisco), `fpga-kit` (FPGA / microcontroller kit), `plc-trainer` (Siemens S7). Environment: `quiet` (Quiet zone), `accessible` (Wheelchair accessible). Staff set them when adding or editing a workstation; any other id is refused.
- GET /api/features is public: it returns only the fixed feature labels, no user or database data.

## The model feature
<!-- Which model, which modality, and what it does for a user.
     Name three things or the check fails: the input it receives, the output it produces,
     and what happens when the model is slow, rate-limited or wrong. -->
- Model: Gemini, text, through the Gemini API (`generativelanguage.googleapis.com`, called with plain `fetch`, no SDK), with the key in `GEMINI_API_KEY` and the model id in `GEMINI_MODEL` (default `gemini-3.5-flash-lite`, a stable model that thinks minimally by default; `gemini-2.5-flash` is retired on 2026-12-01) so it can change without code changes; called only from `src/services/suggest.js`. Chosen because the course gives a free key and the model can return JSON we validate. The key is on the free tier, shared with the class, so a 429 (quota used up) is expected and ends in the fallback like any other failure. Requests are capped at 300 characters, output at `maxOutputTokens: 200` (no thinking setting is sent, so the model's own default applies; a reply cut off at the cap counts as a failure), and each student at 10 suggestions per day, so one student cannot use up the shared quota. Every request that reaches the model counts, including ones that time out or fail; requests refused before the call (empty text, over 300 characters, limit reached) do not count. The count lives in the `suggestion_requests` table (user id, time, outcome: ok, timeout, 429, 503, truncated, invalid, error), never the request text, and the day resets at midnight Europe/Sofia. It turns a plain-language request into one concrete free slot.
- Input: the student's request text (max 300 characters), today's date, and the free slots in the same 14-day booking window, grouped by date and block to keep the prompt small: for each date and block, the free workstations with slot id, lab name, workstation label and features by their labels (e.g. "Quiet zone", "NVIDIA GPU (CUDA)"), so a request like "a PC for deep learning" can match; the instructions give the id of every label. No name, email, user id or anyone's bookings ever leave the app; the request text is never written to logs, only the outcome listed above.
- Output: JSON `{ "slotId": ..., "features": [...], "reason": "..." }`, where `features` lists the ids of the requested features that the workstation has (it may be empty). Before the student sees it, the service checks that the JSON parses, that `slotId` is one of the slots that were sent, that the slot is still free right now, that every id in `features` is on the fixed list and belongs to that workstation, and that `reason` is plain text under 200 characters. The reason's wording is not checked. Anything else counts as a failure. The suggestion is shown with a Book button and, apart from the model's reason, the workstation's real features from the database, labelled so the student can tell the facts from the model's words; nothing is written until the student presses Book.
- When it fails: no key, a timeout after 8 seconds, a 429 (rate limit, or the shared free-tier quota used up) or 503 (overloaded), any other provider error, a truncated response (`finishReason: MAX_TOKENS`), a blocked or refused answer, or an output that fails the checks all end the same way: the student sees "Suggestions are not available right now. Pick a free slot from the list below." and the normal day view for the requested day. While waiting, the button is disabled and shows "Finding a slot…". At the daily limit the model is not called at all and the student sees "You have used today's 10 suggestions. Pick a free slot from the list below." Tests use a fake model client (correct slot, unknown slot, broken JSON, truncated, refusal, hang, 429, 529) and a local stand-in for the Gemini API (the real request shape, 429 without a retry, 503, a blocked prompt); the real API is never called in tests.

## Auth
<!-- Local sign-in plus at least one provider. Say how an account signing in both ways stays one account. -->
- Local: sign-up and sign-in with email and password; password at least 10 characters, stored as a bcrypt hash. Wrong email or wrong password gives the same message. Roles: `student` (default) and `staff`; staff is never chosen at sign-up.
- Provider: Sign in with Google, authorization-code flow on the server, with `state` and PKCE. The OAuth client stays in Testing mode; Google sign-in is shown on the stable deployed URL, local development uses the password.
- Linking: one row in `users` per person, zero or more rows in `identities` (provider + provider account id). Google sign-in first looks up the Google account id. If unknown and Google marks the email as verified, it is linked to the existing user with that email; if not verified, it is never linked and sign-in is refused with a readable message. Because local sign-up does not verify email, a password set before the first Google link is cleared and other sessions end (someone who pre-registered another person's email loses access). The person, now signed in through Google, sets a new password at `/account`, and from then on both ways sign in to the same account. Changing an existing password at /account requires the current one; an account with no password (after a Google link) sets one without it.

## Architecture

One request, `POST /api/bookings`, from the Book button to the database and back:

1. Browser: `public/day.html` shows the day view. `renderBlock()` in `public/day.js` reads the signed-in user from `renderNav` and shows a Book button only on Free blocks. `book()` reads the date from `dateInput` and sends `{ workstationId, date, block }` through `api()` in `public/api.js`, the only function that talks to the server.
2. `src/app.js` parses the JSON body with `express.json()` and mounts the session middleware. In `src/routes/session.js`, `loadUser` turns the cookie into `req.user`, and `requireSignIn` answers 401 if there is none (AC-32).
3. `src/routes/bookings.js` passes `req.user` and `req.body` to `createBooking` and answers 201 with the result. No rules live here.
4. `src/services/bookings.js` `createBooking` applies every rule in order: staff 403, malformed 400, time window 400, unknown workstation 404, out of service 409. Then, inside one transaction: same block 409, 3-booking limit 409, slot already taken 409, and the insert.
5. `src/data/db.js` opens the transaction; `src/data/users.js` `lockForUpdate` locks the student's row so two parallel requests cannot both pass the limit; `src/data/bookings.js` runs the SQL.
6. The database has the last word: the partial unique indexes from `migrations/002_bookings.sql` refuse a second active booking for the same workstation or the same student in a block. If a race gets past the checks, the service catches the violation and maps the index name to the AC-3 or AC-5 message.
7. Back to the browser. On success, `day.js` gets 201 with the booking as JSON, shows "Booked NL-01 on …", and calls `load()`, which fetches the day again with `GET /api/slots`, so the block now shows as Yours. On failure, `src/routes/errors.js` has turned the service's error into a status code and a readable `{ "error": ... }`, and `day.js` shows that sentence.

Where my code does not follow this layering: `staffOnly` in `src/routes/pages.js` checks the role in a route, so the rule "who is staff" lives in two places. It decides only whether the staff HTML page is served: a student gets 403 and `forbidden.html` and never reaches it. Every staff API call is still refused by the services, so even without this check a student could not read or change staff data. Moving it would mean a service call just to serve static HTML, so I kept it and named it here.

## Acceptance criteria

- [AC-1] A signed-in student who opens `/day?date=` for a weekday within the next 14 days sees every active workstation with its features and its six blocks, each marked Free, Taken, Yours (their own active booking) or Past (start time has passed), matching the `bookings` table; only Free blocks have a Book button.
- [AC-2] A student who presses Book on a free upcoming block sees it in `/my-bookings`, and exactly one new row with status `active` appears in `bookings` for that workstation, date and block.
- [AC-3] When two students send a booking for the same block at the same moment, one gets 201 and the other gets 409 with "This workstation was just booked. Pick another slot."; `bookings` holds exactly one active row for that block. (Proved by a test with two parallel requests, not by hand.)
- [AC-4] A student with 3 upcoming active bookings who tries a fourth gets 409 and the message "You already have 3 upcoming bookings. Cancel one first."; no row is added.
- [AC-5] A student who already has a booking in a block and tries another workstation in the same block gets 409 and "You already have a booking at this time."; no row is added.
- [AC-6] A request to book a block whose start time has passed (including the current block, e.g. 10:00–12:00 at 10:30), a weekend, or a date more than 14 days ahead gets 400 with a readable reason and adds no row.
- [AC-7] A student who cancels their own booking before its block starts no longer sees it in `/my-bookings`, its row has status `cancelled`, and the block shows Free in the day view.
- [AC-8] A student who tries to cancel their own booking after its block has started gets 409 and "This booking has already started."; the row stays `active`.
- [AC-9] A student who sends `DELETE /api/bookings/:id` for another student's booking gets 403 and the row stays `active`. (Staff are allowed: see AC-28.)
- [AC-10] A student who opens `/staff/labs` or calls `POST /api/labs` gets 403 and no row is added to `labs`.
- [AC-11] A staff member who adds a lab on `/staff/labs` sees it in `/labs`, and a new row appears in `labs`.
- [AC-12] A staff member who adds a workstation with the features `quiet` and `dual-monitor` sees them in the day view; a request with a feature id outside the fixed list in Constraints (e.g. the old `gpu`) gets 400 and adds no row.
- [AC-13] A staff member who takes a workstation with no upcoming bookings out of service no longer sees it offered in the day view; one with upcoming bookings is refused with "Cancel its N upcoming booking(s) first." (singular "booking" when N is 1) and stays in service.
- [AC-14] A staff member who opens `/staff/bookings?date=` sees every active booking for that day with the student's email.
- [AC-15] A student who calls `GET /api/admin/bookings` gets 403 and no booking data.
- [AC-16] A staff member who calls `POST /api/bookings` gets 403 with "Staff accounts cannot book workstations."; no row is added.
- [AC-17] A student who asks for a suggestion and the fake model returns a free slot sees that slot with a Book button and a short reason; no booking row is created until Book is pressed.
- [AC-18] When the model times out, returns 429 or 503, has no key, stops at the output cap, or returns a slot id that is not free, the student sees "Suggestions are not available right now. Pick a free slot from the list below." and the day view; no booking is created.
- [AC-19] A person who signed up with a password and later signs in with Google using the same verified email lands on the same account and sees the same bookings; `users` still has one row for that email, `identities` has one Google row for it, and the old password no longer signs in.
- [AC-20] A person signed in through Google who sets a new password at `/account`, signs out and signs in with that email and password lands on the same account with the same bookings.
- [AC-21] A Google sign-in whose email Google does not mark as verified is not linked to an existing account, shows a readable refusal, and adds no row to `identities`.
- [AC-39] A signed-in user whose account has a password who tries to change it at /account with a wrong current password gets 403 and "Your current password is not right."; password_hash does not change.
- [AC-22] The MCP tool `cancel_booking` called with a student's token and another user's booking id returns the same 403 error as the HTTP route, and the row stays `active`.
- [AC-28] A staff member who presses Cancel on a student's upcoming booking in `/staff/bookings` sees it disappear from the list; the row has status `cancelled` and `cancelled_by` holds the staff user's id, and the student sees it in `/my-bookings` marked "Cancelled by lab staff".
- [AC-29] A student who already has 10 rows in `suggestion_requests` for today (Europe/Sofia) and asks for an 11th suggestion sees "You have used today's 10 suggestions. Pick a free slot from the list below." and the day view; the fake model client records no call and no row is added to `suggestion_requests`.
- [AC-30] The MCP tool `cancel_booking` called with a staff user's token and a student's upcoming booking id cancels it: the row has status `cancelled` and `cancelled_by` holds the staff user's id, the same as AC-28 in the web UI.
